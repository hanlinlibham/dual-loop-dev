# 真实工程脱敏案例集（Failure Casebook）

以下五个典型场景均提炼自多轮复杂工程实战，展示了单层循环为何失效，以及 `dual-loop-dev` 如何拦截并低成本恢复。

---

## 案例 1：十项自动化检查全绿，冷审阅反向探针抓出流水线自相矛盾

- **现象**：在一次模板脱敏功能轮（第 2 轮）中，类型检查、静态检查、构建、150+ Node 测试与 140+ Python 测试共十项冻结检查全部退出码为 `0`。
- **拦截过程**：全新派出的冷审阅者没有止步于全绿回执，而是阅读清洗流水线并用带数字的业务名称做反向探针——发现步骤 A 先把含数字的系列名改写为占位符 `系列1`，步骤 B 的词表替换又命中了词根 `系列` 将其清成空字符串 `""`，而自检守卫恰好漏检了空系列名。
- **双层处理**：审阅者给出 `reject`（`ATTRIBUTION: code`）；监督者保持验收标准一字不改，在预算第 3 轮只修该落盘逻辑并补齐空串自检守卫，第 3 轮冷审阅复现反例确认修复后 `accept`。

## 案例 2：合同本身写错——归因为 `contract`，实现代码零重做

- **现象**：新增一条后端动作路由后，执行者在允许修改的 12 个路径内完成了正确实现，但发现两处必败矛盾：
  1. 合同要求「未知模板请求返回非 200」，但行为探针使用的轻量 Mock 引擎对所有合法转发请求固定返回 `200`；
  2. 某个未被列入 `allowed_paths` 的旧测试文件硬编码断言「总路由数 == 28」（新增后应为 `29`）。
- **单层循环的常见错误**：执行者为了凑通过，在业务层塞入针对测试入参的脏特判，或擅自改动白名单外的测试。
- **双层处理**：执行者保持候选干净并交回；监督者原样封存提交一次 `execute`（记录真实失败），独立审阅者核实代码无阻断缺陷、确系合同与白名单遗漏，裁决 `reject`（`ATTRIBUTION: contract`）。第 2 轮监督者修正合同断言并将该路由计数测试加入白名单，候选实现核心逻辑一行未重写即通过验收。

## 案例 3：拆解前端 Hook 引入隐蔽异步竞态

- **现象**：将巨型组件拆分为独立自定义 Hook 时，执行者使用 `ref` 读取「最新渲染值」以避免闭包陈旧，并在自述中注明「我认为等价无影响」，静态检查与既有单测全部通过。
- **拦截过程**：监督者将执行者的「我认为无影响」转化为审阅必查问题；审阅者冷读发现当用户在异步 I/O 返回前快速切换选区时，`ref` 已指向新选区，导致旧响应写回覆盖了新选区状态。
- **双层处理**：驳回后在下一轮补齐 I/O 前后选区身份与修订号比对，并新增纯函数并发时序单测。

## 案例 4：执行者漏调 `execute` 与审阅者额度耗尽中断

- **现象 A**：长上下文执行代理完成全部编码与本地自查后直接输出总结退出，忘记运行最终的 `controller.py execute`，控制状态停留在 `issued`。
  - **框架机制**：`orchestrator.py` 检测到执行代理退出后仍处 `issued` 且 `auto_submit_unexecuted=true` 时，自动代执行一次 `execute` 封存候选进入 `awaiting_review`，既不丢弃成果也不允许二次偷改。
- **现象 B**：审阅代理跑到一半遭遇模型 API 速率/额度限制中断退出，未写入 `observations.json` 也未下裁决。
  - **框架机制**：由于审阅阶段对被审仓库完全只读、候选快照已封存，`orchestrator.py` 安全重派全新审阅代理（`max_reviewer_retries`）从头独立复审，无需重跑执行轮。

## 案例 5：共享工作树并发合并引发 `HEAD` 漂移作废

- **现象**：两个会话同时操作同一主仓库 checkout，会话 B 在会话 A 处于 `awaiting_review` 期间执行了 `git merge --ff-only` 并重启了共享开发端口，导致会话 A 的 `HEAD` 校验直接失败作废。
- **框架机制**：
  1. 动手前强制跑 `preflight.py` 检测活跃 `state.json`、近期会话写入与 `LOCK`；
  2. `roadmap.py` 与 `worktree.py` 默认在仓外创建独立 Git Worktree（`supervised/<task-id>`）并分配独立空闲端口，待全部轮次验收通过、主仓空闲后再通过 `worktree.py integrate` 校验审阅尾注合入。
